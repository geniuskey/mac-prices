# 데이터 입력 가이드

가격 데이터는 사람이 apple.com/kr 에서 직접 확인해 넣는다. 이 문서는 그 절차와
검사 항목을 정리한다.

## 왜 수동인가

크롤링은 페이지 구조 변경에 취약하고, 잘못된 값이 들어가도 알아채기 어렵다.
가격은 이 사이트의 유일한 실질 콘텐츠이므로 **틀린 값이 조용히 들어가는 것이
비어 있는 것보다 나쁘다.** 대신 CI 검증과 `verified` 플래그로 상태를 추적한다.

## 검증 수준은 두 단계로 나눠 추적한다

| 필드 | 뜻 |
|---|---|
| `verified` + `verifiedSource` | **기본 구성 정가**를 무엇과 대조했는가 |
| `upgradesVerified` | **BTO 업그레이드 단가**를 대조했는가 |

`verifiedSource` 는 근거의 세기를 구분한다.

- `apple-kr` — apple.com/kr 에서 직접 확인. 유일하게 안심할 수 있는 수준
- `press` — 출시 보도자료·언론 기사. 기본 구성 정가는 대체로 정확하지만
  파생 구성과 업그레이드 단가는 거의 다루지 않는다
- `retail` — 유통 시세. 정가와 다를 수 있다

기본 정가와 업그레이드 단가를 나눈 이유는 **따로 움직이기 때문**이다. 2026년 6월
Apple 은 기본 정가와 별개로 메모리 업그레이드 가격을 두 배로 올렸다
(16→32GB 68만원, 48→128GB 154만원 → 309만원). 정가만 맞다고 업그레이드
단가까지 맞다고 볼 수 없다.

## 2026-06-25 전 라인 가격 인상

메모리·저장장치 부품값 급등으로 Apple 이 맥 전 제품 가격을 올렸다. 한국 기준
최저가 구성 인상 폭은 다음과 같다.

| 제품 | 인상 전 | 인상 후 |
|---|---|---|
| Mac mini | 89만 | 134만 9천 |
| Mac Studio | 329만 | 429만 |
| iMac | 199만 | 249만 |
| MacBook Air 13 | 179만 | 219만 |
| MacBook Air 15 | 209만 | 249만 |
| MacBook Pro 14 | 269만 | 329만 |
| MacBook Pro 16 | 369만 | 499만 |

**보도는 각 제품군의 최저가 구성만 다룬다.** 파생 구성까지 채우지 않으면 상위
구성이 기본 구성보다 싸 보이는 엉터리 표가 되므로, 같은 인상 폭을 적용해 채우고
`estimated: true` 로 표시했다. 화면과 `validate` 출력에 그대로 드러난다.

## 현재 상태

- 기본 정가: **35/39 대조 완료, 전부 `press` 수준.** apple.com/kr 직접 확인은
  아직 하나도 없다.
- 현재가가 추정치인 구성: **10/87.** 위 인상의 파생 구성들이다.
- BTO 업그레이드 단가: **0/39.** 전부 추정값이다. 동일 조건 비교에 나오는
  업그레이드 금액은 참고용으로만 봐야 한다.

```
npm run validate    # 두 단계 각각의 진행률과 미대조 목록을 출력한다
```

가장 값어치 있는 다음 작업은 **현행 판매 모델의 업그레이드 단가를 실제로
입력하는 것**이다. 그래야 동일 조건 비교가 신뢰할 수 있는 숫자가 된다.

## 기존 모델 가격 대조하기

1. `data/models/<제품군>/<모델>.json` 을 연다.
2. 파일의 `sourceUrl` (Apple 기술 사양) 과 Apple 온라인 스토어의 구매 페이지를
   나란히 연다.
3. `configs` 의 각 항목을 스토어의 기본 구성과 대조한다.
   - `chipId` — CPU/GPU 코어 수가 `data/chips.json` 의 해당 칩과 맞는가
   - `memoryGb` / `storageGb`
   - `prices` 의 마지막 항목이 **현재 정가**와 같은가
4. `upgrades` 의 업그레이드 단가를 스토어 구성 화면에서 확인한다.
   메모리·저장장치를 한 단계씩 올려보며 증가액을 적는다.
5. 기본 구성 정가가 맞으면 `"verified": true`, `"verifiedSource": "apple-kr"`
   로 바꾸고 `checkedAt` 을 오늘 날짜로 갱신한다.
6. 업그레이드 단가까지 확인했으면 `"upgradesVerified": true` 로 바꾼다.
7. `npm run validate` 를 돌린다.

### 정가가 바뀌었다면

기존 항목을 **고치지 말고 뒤에 추가**한다. 가격 이력이 사이트에 그대로 노출되고,
단종 모델의 과거 가격이 중고 시세 기준으로 쓰인다.

```json
"prices": [
  { "krw": 2690000, "effectiveFrom": "2024-11-08" },
  { "krw": 3290000, "effectiveFrom": "2026-06-25", "note": "환율 인상" }
]
```

`effectiveFrom` 은 반드시 오름차순이어야 한다 (validate 가 검사한다).

## 새 모델 추가하기

1. 필요하면 `data/chips.json` 에 칩을 먼저 추가한다.
   **코어 수 바인닝마다 별도 레코드**를 만든다. 예를 들어 M4 Pro 12코어와
   14코어는 서로 다른 `id` 를 갖는다. 그래야 구성이 칩 하나를 정확히 가리킨다.
2. `data/models/<제품군>/<모델-id>.json` 을 만든다. 같은 제품군의 기존 파일을
   복사해 고치는 게 빠르다.
3. `id` 는 `<제품군>-<크기>-<칩>-<연도>` 꼴로 짓는다. 예: `mbp-14-m4-pro-max-2024`
4. 파일이 놓인 디렉터리 이름과 `family` 값이 같아야 한다 (validate 가 검사한다).
5. `isBaseConfig: true` 는 **정확히 하나**여야 한다 — 그 모델의 최저가 구성.
6. 이전 세대 모델 파일에 `discontinuedAt` 을 채운다.

### 포트 구성이 다르면 파일을 나눈다

`ports` 와 `display` 는 모델 단위 속성이다. 같은 크기라도 구성에 따라 포트 수가
다르면 별도 모델로 분리한다. 예를 들어 14인치 MacBook Pro 는 기본 M4 가
Thunderbolt 3개, M4 Pro/Max 가 Thunderbolt 5 3개로 달라서
`mbp-14-m4-2024` 와 `mbp-14-m4-pro-max-2024` 로 나눠져 있다.

### 구성은 같고 가격만 다르면 variantLabel 을 쓴다

Mac Pro 타워/랙, iMac 2포트/4포트처럼 칩·메모리·저장장치가 같은데 가격이 다른
경우 `variantLabel` 로 구분한다. 이 값이 없으면 validate 가 중복 구성으로 막고,
동일 조건 비교에서 한쪽이 다른 쪽을 가린다.

## 업그레이드 표 작성 요령

동일 조건 비교는 `upgrades` 에 **정확히 일치하는 from → to 쌍**이 있어야
동작한다. 계산기는 중간 단계를 이어붙이지 않는다.

기본 구성이 256GB 인데 사용자가 1TB 로 비교하고 싶다면
`{ "kind": "storage", "fromValue": 256, "toValue": 1024 }` 항목이 있어야 한다.
`256→512` 와 `512→1024` 만 있으면 "구성 불가" 로 표시된다.

그래서 각 기본 구성의 출발점에서 **모든 상위 용량까지의 쌍**을 넣는다.
칩에 따라 단가가 다르면 `chipId` 를 지정한다.

## 검증 항목

`npm run validate` 가 막는 것들:

- 스키마 위반 (필수 필드 누락, 잘못된 날짜 형식, 가격이 정수가 아님)
- 존재하지 않는 `chipId` 참조
- 중복 모델 `id`, 중복 구성
- `isBaseConfig` 가 0개거나 2개 이상
- 디렉터리 이름과 `family` 불일치
- `prices` 가 오름차순이 아님
- 칩의 메모리 상한을 넘는 구성
- `toValue <= fromValue` 인 업그레이드

CI 에서 이 스크립트가 실패하면 머지되지 않는다.

## 업그레이드 단가에는 이력이 없다 — 알려진 한계

`configs.prices` 는 `effectiveFrom` 스냅샷 배열이라 정가 변동을 담지만,
`upgrades.krw` 는 단일 값이다. 2026-06 메모리 업그레이드 가격 인상 같은 사건은
표현할 수 없다.

지금은 업그레이드 단가가 전부 미대조 추정값이라 문제가 드러나지 않는다. 실제
값을 채우기 시작하면 `upgrades` 에도 `configs` 와 같은 `prices` 배열을 주는
편이 낫다. 단종 모델은 단종 시점 단가를, 현행 모델은 현재 단가를 각각
정확히 담을 수 있다.
